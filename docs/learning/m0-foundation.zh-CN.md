# M0：项目起点与架构选择

日期：2026-07-23

对应 commit：`a37e23c initialize epiphany studio`

## 1. 为什么先写文档，不先写代码

这个项目同时承担两个目标：

- 做一个真的能帮助个人创作的产品；
- 用它学习 Agent 编排、后端、可靠性、运维和部署。

如果一开始直接写代码，很容易变成“看到什么技术就加什么技术”，最后得到
很多框架，却没有一条能用的产品链路。

M0 先回答：

1. 谁是第一位用户；
2. 第一条工作流解决什么问题；
3. 什么属于 MVP；
4. 什么暂时明确不做；
5. 采用什么最小架构；
6. 什么时候才允许升级架构。

## 2. 产品目标

第一位用户就是项目作者本人。第一类真实素材来自日记、随想、播客素材和
文章。

第一条产品链路是：

```text
真实素材
  -> 有来源的提取
  -> 半开放采访脚手架
  -> 用户继续口述
  -> 播客稿或文章
  -> 用户审核
```

它不是一个“输入主题就自动生成鸡汤文章”的工具。系统必须尽量保留真实
细节、本人语言和证据来源。

## 3. 为什么选择轻量自建编排

当时考虑过：

- LangGraph；
- Temporal；
- Celery + Redis；
- 复用代码 Agent Runtime；
- 用普通后端代码实现一层受限编排。

最终选择最后一种。

生活类比：在只有两名研究员的小团队里，先写清楚任务表和交接规则，比先
购买一套大型跨国公司流程系统更重要。

这个选择不是说大型框架不好，而是当前最需要验证的问题是：

> 这种来源驱动的采访脚手架，对真实创作有没有帮助？

大型框架不能替产品回答这个问题。

## 4. 初始技术选择

| 技术 | 当前作用 | 为什么适合第一版 |
| --- | --- | --- |
| Python 3.12 | 后端语言 | AI SDK 和数据工具成熟 |
| FastAPI | HTTP API | 类型明确，自带 Swagger |
| Pydantic | 输入输出校验 | 适合严格结构化 Agent 输出 |
| SQLite | 本地数据库 | 单用户、零额外服务 |
| SQLAlchemy | 数据访问 | 明确模型和事务边界 |
| Alembic | 数据库 migration | 可以安全演进本地数据库 |
| asyncio | 两个 Child 并发 | 不需要先上任务队列 |
| Fake Provider | 不联网测试 | 先验证 Runtime，不产生费用 |

## 5. 明确没有采用的技术

MVP 暂时没有：

- LangGraph；
- Temporal；
- Celery；
- Redis；
- PostgreSQL；
- Kubernetes；
- 向量数据库；
- 每个 Agent 一个容器。

这减少了安装、部署和调试变量，也迫使我们真正理解：

- Run/Task 状态是什么；
- 谁创建 Child Task；
- 怎样等待和合并；
- 重试、取消和恢复怎样工作；
- 状态到底保存在哪里。

## 6. 关键架构原则

### 数据库是真相来源

内存中的对象和以后前端看到的状态都只是视图。Run、Task、Event 和
Artifact 的真实状态存在数据库。

### 模型不能控制一切

模型将来可以提取主题、发现缺口和组织表达，但以下规则必须由代码控制：

- 允许使用哪些 Agent；
- 最大并发和深度；
- timeout 和 retry；
- 取消传播；
- 输出是否符合 Schema；
- 引用是否来自允许的 Source。

### Agent 只提交候选结果

Agent 不能偷偷改写已确认的长期记忆，也不能自动发布节目。

### 先做固定 Workflow

第一版不做“让模型动态发明无限 Agent”的通用平台，只做一条可理解、
可恢复、可测试的创作流程。

## 7. M0 建立的文档

| 文档 | 作用 |
| --- | --- |
| `README.md` | 项目入口和现状 |
| `docs/product-spec.zh-CN.md` | 产品目标、用户旅程和范围 |
| `docs/architecture.zh-CN.md` | 系统边界和数据流 |
| `docs/roadmap.zh-CN.md` | 小步里程碑 |
| `docs/adr/0001-...` | 为什么选择轻量编排 |
| `AGENTS.md` | AI 和开发者都必须遵守的规则 |

ADR 是 Architecture Decision Record，作用是保存“当时为什么这样选”，
避免未来只看到结论却忘记背景。

## 8. 怎样验证 M0

M0 没有可运行代码，主要通过文档一致性验证：

1. README 能说清楚项目是什么；
2. Product Spec 有具体第一位用户和 MVP；
3. Roadmap 每一步都有演示标准；
4. Architecture 说明模型与代码的边界；
5. ADR 记录选型与复审条件；
6. `.gitignore` 和规范明确不提交密钥与个人素材。

## 9. 这一步学到了什么

- 架构选择应该服务于当前风险，而不是展示技术数量；
- “暂时不做什么”与“要做什么”同样重要；
- 技术决策要记录背景、代价和复审条件；
- 学习型项目也需要真实用户和端到端目标；
- 先写边界能减少 AI 自动扩张范围。

## 10. 当时还没有什么

M0 结束时仍然没有：

- 可启动的后端；
- 数据库表；
- API；
- Worker；
- Agent 调度；
- 前端。

下一步 M1 才开始建立最小可运行的持久化 Runtime。
